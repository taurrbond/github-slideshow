# Skill: refactor

## Цель

Предлагает рефакторинг кода с сохранением существующей функциональности.
**Всегда показывает план изменений и ждёт подтверждения перед применением.**

Фокус — на читаемости, устранении дублирования и упрощении структуры.
Не добавляет новую функциональность и не меняет публичный API.

## Как вызвать

```
/refactor [путь к файлу или функции]
```

Примеры:
```
/refactor src/services/user_service.py
/refactor src/components/Header.tsx::renderMenu
```

## Входные данные

| Параметр | Обязателен | Описание |
|----------|-----------|----------|
| `target` | Да | Путь к файлу или `файл::функция` |
| `--goal TEXT` | Нет | Конкретная цель: `"убрать дублирование"`, `"упростить условия"` |
| `--safe` | Нет | Только переименования и форматирование (минимальный риск) |

## Алгоритм выполнения

1. **Анализ** — прочитать файл, выявить проблемы по категориям ниже.
2. **План** — вывести список предлагаемых изменений с обоснованием.
3. **Подтверждение** — дождаться явного `yes` / `apply` от пользователя.
4. **Применение** — внести изменения строго по плану, не шире.
5. **Верификация** — запустить существующие тесты, убедиться что всё зелёное.

> Шаги 3-5 выполняются только после подтверждения.

## Категории проблем (чеклист анализа)

### Дублирование
- Одинаковые блоки кода в разных местах → извлечь в функцию/метод.
- Повторяющиеся магические числа/строки → вынести в константы.

### Сложность
- Функции длиннее 30 строк → разбить на меньшие.
- Вложенность больше 3 уровней → ранний возврат (`guard clause`).
- Длинные условия → именованные предикаты или переменные.

### Именование
- Неясные имена (`data`, `tmp`, `res`) → конкретные имена.
- Несоответствие стилю проекта (snake_case vs camelCase).

### Структура
- God-функции (делают слишком много) → принцип единой ответственности.
- Лишние комментарии, объясняющие очевидное → удалить.
- Мёртвый код → удалить.

## Выходной формат

### Фаза 1 — план (всегда выводится первой)

```
## Рефакторинг: src/services/user_service.py

### Найденные проблемы

1. **Дублирование** (строки 45-52 и 89-96)
   Блок валидации email повторяется дважды.
   → Извлечь в `_validate_email(email: str) -> bool`

2. **Сложность** (функция `process_user`, 67 строк)
   Функция делает валидацию, запись в БД и отправку письма.
   → Разбить на `_validate()`, `_save()`, `_notify()`

3. **Именование** (строки 12, 34, 78)
   Переменная `d` → переименовать в `user_data`

4. **Мёртвый код** (строки 100-108)
   Функция `legacy_format()` не вызывается нигде.
   → Удалить

### Что НЕ меняется
- Публичный API (`process_user`, `get_user_by_id`)
- Логика валидации и бизнес-правила
- Формат возвращаемых данных

Применить изменения? (yes / no)
```

### Фаза 2 — применение (только после `yes`)

```
## Применено

✓ Извлечена функция `_validate_email` (строки 45-52, 89-96)
✓ `process_user` разбита на 3 вспомогательные функции
✓ Переменная `d` → `user_data` (3 вхождения)
✓ Удалена `legacy_format` (8 строк)

### Тесты
$ pytest tests/test_user_service.py -v
.......... 10 passed in 0.43s ✓
```

## Правила безопасности

- **Никогда** не менять поведение — только структуру.
- **Никогда** не применять изменения без подтверждения.
- Если тесты отсутствуют — предупредить перед применением:
  > ⚠️ Тесты не найдены. Рефакторинг без тестов рискован. Продолжить?
- Если изменение затрагивает публичный API — явно указать это в плане.
- Применять изменения одной операцией, не по частям.
